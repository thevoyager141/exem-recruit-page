저희 데몬3팀은 고객의 복잡한 IT 환경에서 발생하는 다양한 성능 데이터를 안정적으로 수집하고, 이를 실시간으로 분석 가능한 형태로 전달하는 기반의 에이전트을 개발하는 팀입니다.


exemONE은 인프라, 네트워크, 컨테이너, Kubernetes, APM, DB 등 통합 모니터링 솔루션이며, InterMax는 애플리케이션 성능 및 End-to-End 트랜잭션 분석 솔루션입니다. 저는 이 중에서 인프라, 네트워크, APM/TP 영역의 에이전트에서 실제 데이터를 수집하는 로직을 개발하고 있습니다.


인프라 영역에서는 고객의 서버에 설치되어 CPU, 메모리, 네트워크, 디스크 등의 시스템 자원 데이터를 각 OS 환경에 맞게 동일한 스펙의 데이터로 수집하는 Host 에이전트를 개발하고 있습니다. 또 장시간 고객의 서버에서 직접 동작하는 에이전트 특성상 성능 오버헤드를 최소화하면서 안정성을 유지하는 구조를 만드는 데 집중하고 있습니다. 이를 통해 고객은 OS별 명령어나 개별 도구 없이도 통합 화면에서 서버 상태를 일관되게 확인할 수 있습니다.


네트워크 영역에서는 여러 네트워크 장비에서 SNMP 통신을 기반으로 표준 성능 지표뿐만 아니라, 장비별로 제공되는 고유 성능 지표까지 수집하는 NDM 에이전트를 개발하고 있습니다. 이를 통해 고객은 다양한 제조사의 네트워크 장비를 하나의 통합 화면에서 일관되게 모니터링할 수 있으며, 트래픽 부하나 성능 이상 구간을 빠르게 파악할 수 있습니다.


APM/TP 영역에서는 TMAX와 TUXEDO 기반 서비스의 트랜잭션 및 성능 데이터를 수집하고 이를 End-to-End 트랜잭션 분석과 연계할 수 있도록 TP 모니터링 에이전트를 개발하고 있습니다. 단순한 지표 수집이 아니라 트랜잭션 흐름을 연결할 수 있는 데이터를 수집하는 것이 핵심이며 이를 통해 고객은 복잡한 애플리케이션 구조에서도 병목이나 지연이 발생하는 구간을 빠르게 분석할 수 있습니다.

* 해결 과정에서 얻은 교훈이나 이후 코드/구조 개선 포인트에 대해 말씀 부탁드립니다.


고객 환경이 워낙 다양하다 보니 예상과 다르게 동작했던 경험은 많이 있습니다. 특히 기억에 남는 사례는 인프라 호스트 에이전트와 TP 모니터링 에이전트에서 발생한 문제입니다.


먼저 exemONE의 호스트 에이전트는 Linux, AIX, HP-UX, SunOS, Windows 등 다양한 운영체제를 지원하고 Linux만 해도 배포판과 버전이 매우 다양합니다. 실제로 특정 배포판이나 버전에서는 일부 성능 지표가 수집되지 않거나, 반대로 예상보다 많은 데이터가 수집되어 내부 버퍼 구조를 초과하는 문제가 발생한 적이 있었습니다.
이 경험을 통해 특정 환경을 기준으로 고정된 구조는 결국 한계를 가질 수밖에 없다는 것을 배웠습니다. 이후에는 특정 OS 버전에 맞춘 예외 처리 방식이 아니라 통합적으로 대응할 수 있는 구조로 로직을 개선하는 방향으로 우선 고민하게 되었습니다. 


TP 모니터링 영역에서도 비슷한 경험이 있었습니다. TMAX나 TUXEDO 기반 서비스는 고객의 서비스 구성 방식에 따라 다양한 환경을 접할 수 있습니다. TMAX 사용하는 일부 고객 환경에서는 환경 구성으로 인해 서버/서비스 목록 수집 결과가 예상과 다르게 수집되거나 SQL 및 bind 변수 수집이 누락되는 사례가 있었습니다. 이런 경우 에이전트에 예외처리 로직을 추가하여 해결한 경험이 있습니다.

* 폭넓은 기술 경험이 현재 개발 업무에 어떤 도움이 되고 있는지 설명 부탁드립니다. 
* JD 키워드 중 “IT 인프라 전 영역”, “폭넓은 기술 스택” 기반 질문 입니다.


EXEM에 입사하기 전에는 Linux 기반 환경에서 C언어로 에이전트 개발을 주로 했습니다. 하지만 EXEM에 입사한 이후에는 C언어를 제외하면 기존 경험과 겹치는 영역이 거의 없을 정도로 다양한 기술 분야를 접하게 되었고 지난 5년 동안 개발자로서 시야가 많이 넓어진 것 같습니다.


입사 초기에는 TP 모니터링을 담당했는데, 당시 저에게 완전히 새로운 영역이었습니다. TMAX, TUXEDO 기반 TP 미들웨어 구조, 트랜잭션 흐름 등을 이해해야 했습니다. 특히 TP 모니터링을 위한 기반기술은 저에게 생소한 부분이였기 때문에 원리를 이해하기까지는 조금 시간이 걸렸지만 다른 곳에서는 접할 수 없는 기술 경험이 였습니다. 그리고 부하 트랜잭션을 안정적으로 수집하기 위한 데이터 구조와 수집 로직들을 배울 수 있었습니다.


인프라 모니터링 영역에서는 AIX, HP-UX, SunOS, Linux, Windows 등 다양한 운영체제를 직접 다루었습니다. 같은 C 언어로 개발하더라도 OS마다 커널 인터페이스, 시스템 API, 프로세스/메모리 구조, 성능 지표 수집 방식이 완전히 다르기 때문에, 각 운영체제의 내부 동작과 구조를 깊이 이해하는 계기가 되었습니다.


네트워크 영역에서는 SNMP 기반 장비 모니터링을 담당하며 MIB 구조, OID 체계, 인터페이스 성능 지표 등 네트워크 장비 특성을 배울 수 있었습니다.


또한 제가 담당하는 에이전트는 고객 서버에서 직접 실행되기 때문에 패치가 쉽지 않은 특성이 있습니다. 따라서 개발 단계부터 성능 오버헤드와 장시간 운영 안정성을 최우선으로 고려해야 했습니다. 메모리 사용, CPU 부하, 리소스 누수 가능성을 체크하여 안정성을 중심으로 아키텍처를 설계하는 경험을 쌓을 수 있었습니다.


최근에는 Python 모니터링 에이전트 개발을 통해 컨테이너 및 Kubernetes 환경을 접하게 되었고, 아직 학습 중인 영역이지만 기존 개발 에이전트에도 접목하면서 점점 이해 범위를 넓히려고 노력하고 있습니다.


EXEM에서 제가 담당하는 에이전트들은 모두 모니터링이라는 공통 목적을 가지지만 각기 다른 기술 영역을 다룹니다. 덕분에 많은 기술들을 접할 수 있었고 성장 할 수 있었습니다.
	



Q5. 24시간 운영 환경에서 항상 동작해야 하는 C기반 Agent를 개발할 때 가장 중요하게 지키는 원칙이 있다면 무엇인가요?
[답변 작성 시 참고]
* 성능 overhead를 최소화하기 위한 기준
* 장애나 예외 상황 발생 시 복구 방식
* 안정적인 데이터 수집을 위해 중요하게 생각하는 가치


제가 담당하는 에이전트는 고객 서버에서 직접 실행되기 때문에 패치가 쉽지 않습니다. 일부 환경에서는 에이전트 장애가 곧 서비스 영향으로 이어질 수 있기 때문에 개발 단계부터 성능 오버헤드와 안정성을 가장 중요한 기준으로 생각합니다.
그래서 메모리 사용량, CPU 부하, 리소스 누수 가능성을 꼭 점검하고, 팀 테스트 환경에서도 단기 테스트가 아니라 장시간 실행 테스트를 통해 안정성을 검증하려고 노력합니다.


가장 중요한 원칙은 “죽지 않는 에이전트”를 만드는 것입니다. 예외 상황이 발생하더라도 에이전트가 종료되지 않도록 예외 처리를 꼼꼼하게 하려고 노력합니다.


또 하나 중요한 부분은 하위 호환성 유지입니다. 패치가 어려운 환경이기 때문에, 새로운 기능을 추가할 때도 기존 수집 구조와 프로토콜이 깨지지 않도록 항상 고려해야합니다. 최신 에이전트와 구버전 수집 서버가 함께 운영되더라도 문제 없이 동작해야 하기 때문에, 기능 확장도 중요하지만 항상 호환성과 안정성을 우선 생각합니다.

이 과정에서 GPT나 Claude와 같은 AI 도구도 활용했습니다. 단순히 답을 얻기 위한 용도가 아니라 샘플 환경 구성이나 개념 확인, 실습 과정에서의 가이드 역할로 활용하여 스터디 속도를 높일 수 있었습니다.

Q10. 마지막으로, 엑셈에 합류를 고민하시는 분들에게 한 말씀 부탁드려요.
[답변 작성 시 참고]
* C기반 시스템 개발을 좋아하는 분들에게 매력 포인트가 있다면?
* 지원을 망설이는 분들께 용기를 주는 메시지를 자유롭게 작성해 주시면 좋겠습니다.


저는 오랫동안 C기반 에이전트 개발을 해왔고, 최근 몇 년은 Python기반 모니터링 에이전트도 함께 개발하고 있습니다. Python은 다양한 기능이 이미 라이브러리로 제공되어 있어서 C로 수십 줄 혹은 수백 줄 작성해야 할 로직을 훨씬 간결하게 구현할 수 있다는 장점이 있습니다. 개발 접근성 측면에서는 Python이 분명 편리한 언어라고 생각합니다. 하지만 Python 인터프리터는 C로 구현되어 있고, 많은 시스템 라이브러리도 C기반입니다.


최근에는 C기반 로그 모니터링 기능을 추가 개발한 경험이 있습니다. 기존에는 동일한 기능이 Go 언어로 먼저 구현되어 있었고 Go에서는 goroutine을 활용한 매우 유연한 병렬 구조를 사용하고 있었습니다. 같은 기능을 C 환경에서는 goroutine처럼 가벼운 병렬 구조를 그대로 가져올 수 없기 때문에 thread pool 기반 구조로 아키텍처를 설계 했습니다. 작업 큐와 스레드 풀을 분리하고, I/O 처리와 파싱 로직을 단계별로 나누어 제한된 자원 안에서 안정적으로 동작하도록 로직을 구현했습니다. 이 과정에서 운영체제의 스케줄링 방식, 스레드 비용, 컨텍스트 스위칭, 락 경합, 메모리 사용 패턴 같은 시스템 레벨 요소의 깊은 이해가 필요했습니다.


이런 경험을 통해 제가 느낀점은 C기반 개발은 분명 어렵지만 그만큼 시스템을 깊이 이해하는 개발자가 될 수 있다는 것입니다. 메모리, 성능, 구조를 직접 설계하고 최적화하는 경험은 어떤 언어를 사용하더라도 큰 기반이 될 수 있다고 생각합니다.


EXEM의 에이전트 개발은 단순한 애플리케이션 개발이 아니라, 실제 고객 서버에서 동작해야 하는 시스템 에이전트를 만드는 일입니다. 그래서 C기반 시스템 개발을 좋아하는 분들에게는 매우 흥미로운 환경이 될수 있을거라고 생각합니다. 동시에 Kubernetes, 네트워크, APM 등 다양한 영역을 계속 접할 수 있기 때문에 기술적으로 폭넓게 성장할 수 있습니다.


EXEM은 개발자로서 다양한 경험을 쌓을 수 있는 좋은 환경이라고 생각합니다.
